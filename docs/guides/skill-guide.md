Skill 设计与评审原则
1. Skill 的本质定位
Skill 是一套面向 Agent 的任务方法与关键行为约束。
它的作用是让 Agent：
* 正确理解当前任务的目标；
* 聚焦完成当前能力；
* 避免已经验证过的典型错误；
* 在合适的条件下结束并交付结果。
Skill 不是：
* 专业知识库；
* 详尽规范汇编；
* 完整 Agent Runtime；
* 状态机实现；
* 所有异常情况的穷举；
* 对模型已有通用能力的重新教学。
判断一段内容是否应该写进 Skill 时，应先问：
删除这段内容后，Agent 是否会显著偏离当前任务目标，或者重复出现已经验证过的执行错误？
答案是否定的，就不应写入 Skill。

2. 核心设计原则
原则一：先定义唯一核心目标
每个 Skill 必须能够用一句话说明：
* Agent 要完成什么；
* 最终结果供谁使用；
* 什么状态表示任务成功。
例如：
将当前会话中已经形成的最终设计，完整、准确地固化为可独立使用的设计稿。
核心目标必须位于 Skill 的高注意力位置，后续所有步骤和规则都应直接服务于该目标。
如果一个 Skill 同时存在多个同等重要的目标，通常说明职责范围过大，应考虑拆分。

原则二：目标优先于流程，流程服务于目标
Skill 不应因为流程形式完整而失去对结果的关注。
设计顺序应当是：
核心目标
→ 已验证的失败模式
→ 最小必要方法
→ 少量关键约束
而不是：
完整流程
→ 状态分类
→ 异常分支
→ 信息模型
→ 最后补充目标
流程存在的目的，是帮助 Agent稳定实现目标，而不是让 Agent机械完成步骤。

原则三：坚持单一职责
一个 Skill 只负责一种稳定能力。
例如：
* 工作流 Skill：负责阶段顺序和能力调用；
* 分析 Skill：负责如何开展分析、讨论和收敛；
* Draft Skill：负责如何把已经形成的设计写成设计稿；
* Guide：负责特定专业领域应分析什么；
* Spec：负责交付文档的结构和内容合同；
* Script、Hook、Lint：负责可以确定性执行和验证的规则。
当前 feature-design 负责编排五个顶层任务，并在步骤 2 调用独立的分析 Skill；feature-design-analysis 只负责分析、讨论和确认，不接管 Draft、Review 和发布。这种职责拆分是正确方向。fileciteturn0file0 fileciteturn0file1
当一个 Skill 开始同时负责上下文恢复、专业分析、产物生成、评审、持久化、状态管理和发布时，应优先判断是否需要拆分，而不是继续增加规则。

原则四：使用最小有效约束
Skill 中只保留以下两类约束：
1. 直接决定任务能否成功的要求；
2. 针对实际使用中已经发生的错误所增加的防护。
不要为了理论完整性提前定义所有可能情况。
规则越多，不代表执行越稳定。对能力较弱的模型，过多规则通常会造成：
* 核心目标被稀释；
* 局部规则相互竞争；
* Agent机械覆盖清单；
* 注意力从任务结果转移到格式符合；
* 看似遵循规则，实际没有完成目标。
新增规则前必须能够回答：
这条规则针对哪一个已经观察到的具体失败？
无法回答时，暂不增加。

原则五：方法论优于详尽清单
Skill 应告诉 Agent“如何完成任务”，而不是穷举任务中可能出现的所有内容。
推荐使用少量线性步骤，每一步只有一个明确目标，例如：
理解当前设计
→ 识别关键问题
→ 与用户讨论
→ 确认完整设计
或者：
恢复最终设计
→ 按模板写入
→ 对照检查遗漏
避免把一个简单方法进一步展开成：
* 十几种信息类型；
* 多套状态；
* 多层覆盖矩阵；
* 大量特殊分支；
* 复杂结构化返回协议。
专业内容越复杂，越应该放入 Guide 或模板，而不是继续扩张通用 Skill。

原则六：充分利用 Agent 已有能力
不要重新教授模型已经具备的通用能力。
例如，模型通常已经理解：
* 什么是设计文档；
* 如何总结一次讨论；
* 如何按照模板写文档；
* 如何分析方案优缺点；
* 如何识别风险和约束。
Skill 应校正的是模型容易误解的任务目标。
例如 Draft 生成失败的核心问题不是 Agent 不知道如何写文档，而是它错误地把“完整固化设计”执行成了“总结设计讨论”。
因此只需要明确：
不要把设计稿写成摘要；必须保留所有仍然有效且影响后续执行的设计信息。
没有证据表明模型无法理解某个概念时，不要提前为该概念编写大量定义。

原则七：专业知识与执行方法分离
通用 Skill 负责方法，专业 Guide 负责领域判断。
例如：
* 业务设计 Guide 定义业务语义、规则、状态和业务结果应如何收敛；
* 方案设计 Guide 定义系统边界、微服务职责、4+1 视图和系统级契约；
* 实现设计 Guide 定义代码级结构、行为、状态、事务和工程约束；
* 测试设计 Guide 定义风险、测试层级、数据、环境和验证要求。fileciteturn0file3 fileciteturn0file4 fileciteturn0file5 fileciteturn0file6
通用 Skill 不应复制这些内容。
正确关系是：
Skill：如何完成任务
Guide：在当前领域分析什么、达到什么专业深度
Spec：最终文档如何组织

原则八：模板是结构约束，不是内容过滤器
Spec 或模板用于组织输出，不应反过来决定哪些有效信息可以被保留。
如果已经形成的有效内容无法自然放入模板：
* 放入最接近的章节；
* 增加必要的子章节；
* 使用附录或交叉引用；
* 必要时指出模板结构不足。
不得因为模板没有明确字段，就删除已经确认的设计信息。
设计语义完整性通常高于模板形式完整性。

原则九：编排与能力调用不要重复定义
父 Skill 调用子 Skill 时，应当是职责迁移，而不是规则叠加。
父 Skill只保留：
* 什么时候调用；
* 提供什么上下文；
* 什么条件下允许返回；
* 返回后进入哪个阶段。
子 Skill负责当前能力的具体方法。
如果父 Skill 和子 Skill 同时定义：
* 相同分析循环；
* 相同提问规则；
* 相同收敛条件；
* 相同分段确认逻辑；
模型将面对两套竞争指令，拆分反而会增加复杂度。
因此拆分 Skill 时应遵循：
移动职责，而不是复制职责。

原则十：Task List 只管理顶层焦点
Task List 的价值是利用 Agent Harness 保持阶段聚焦，例如：
恢复上下文
→ 完成设计
→ 生成 Draft
→ Review
→ 发布
它可以约束当前应完成哪个阶段，但不能自动保证阶段内部的语义质量。
因此：
* 顶层工作流可以使用 Task List；
* 当前任务内部由专用 Skill 提供方法；
* 不要为每个子 Skill 再创建一套嵌套 Task List；
* 不要把所有分析动作拆成大量细粒度任务。
当前 feature-design 使用五个线性顶层任务，并把专业分析委托给独立 Skill，是较合理的 Harness 分层。fileciteturn0file0

原则十一：语义判断与确定性校验分离
适合模型完成的工作：
* 理解语义；
* 分析问题；
* 比较方案；
* 撰写设计；
* 判断内容之间是否一致。
适合脚本、Hook 或 Lint 完成的工作：
* 文件是否存在；
* frontmatter 是否合法；
* 必需章节是否存在；
* 占位符是否残留；
* hash 是否一致；
* 状态转换是否合法；
* 固定格式是否满足要求。
不要在 Skill 中用文字模拟一个没有工具支撑的 Runtime。
例如，模型自行输出：
status: completed
coverage: 100%
并不能证明任务真的完成。
只有存在真实消费者或确定性校验时，才引入结构化状态协议。

原则十二：退出条件必须与核心目标直接对应
Skill 的完成条件应少而明确。
例如设计分析 Skill 的退出条件可以是：
* 关键设计问题已经关闭；
* 完整设计已经确认；
* 用户明确允许进入 Draft。
Draft Skill 的退出条件可以是：
* 最终有效设计已经完整写入；
* 没有过度概括、遗漏或语义变化；
* 文档可以脱离会话独立使用。
不要为显得严谨而增加大量相互重叠的完成条件。
完成条件越多，模型越可能机械声明“均已满足”，而不是实际检查核心结果。

3. 现有 Skill 的分析方法
分析一个现有 Skill 时，按以下顺序进行。
第一步：提取核心目标
尝试用一句话概括该 Skill。
如果无法用一句话说明，检查是否包含多个职责。
重点判断：
* 输出是什么；
* 使用者是谁；
* 成功标准是什么；
* Skill 当前最希望阻止什么错误。

第二步：识别职责分层
将 Skill 内容分别标记为：
* 核心目标；
* 执行方法；
* 关键约束；
* 专业知识；
* 模板要求；
* 确定性操作；
* 工作流编排；
* 异常处理。
然后判断每类内容是否放在正确位置：
内容	推荐位置
目标和方法	Skill
领域知识和专业深度	Guide
文档结构	Spec/Template
可确定性验证规则	Script/Lint/Hook
阶段顺序	Workflow Skill/Task List
当前能力内部方法	专用 Capability Skill
第三步：查找注意力竞争
重点检查：
* 是否同时存在多个核心目标；
* 是否重复描述同一规则；
* 父子 Skill 是否职责重叠；
* Guide 内容是否复制进入 Skill；
* 是否存在大量局部规则掩盖核心目标；
* 是否存在互相矛盾或优先级不明确的要求。
出现这些问题时，优先删除、移动或合并，而不是继续补充解释。

第四步：查找过度设计
以下信号通常表示 Skill 已经开始过度设计：
* 为每类信息设计独立状态；
* 引入没有脚本支持的结构化结果；
* 建立复杂 ID、游标、依赖图或 coverage 文件；
* 为理论上的会话中断设计大量恢复逻辑；
* 为尚未发生的错误增加大量规则；
* 子 Skill 比父工作流还长；
* Skill 大量重复模板或 Guide；
* Agent 必须同时记忆多个模型、状态和退出协议。
发现这些信号时，先回到核心目标，寻找更简单的表达。

第五步：核对实际失败
优化不能只依据理论分析。
应收集：
* Agent 实际做错了什么；
* 哪一条输出证明发生了错误；
* 错误属于目标误解、流程跳过、专业能力不足、上下文丢失还是工具限制；
* 当前 Skill 中哪条指令允许了该错误；
* 最小改动是什么。
不要把模型能力问题、Guide 问题、模板问题、上下文问题和工作流问题混为一谈。

第六步：执行最小修改并验证
每次优先只修改一个关键因素，例如：
* 拆出专用能力 Skill；
* 删除父 Skill 中重复流程；
* 强化一条核心目标；
* 增加一个必要确认门禁；
* 将专业内容移动到 Guide；
* 将格式规则移动到 Lint。
然后使用同一个真实场景对比修改前后的结果。
只有实际结果仍然失败时，再增加下一项约束。

4. 常见反模式
反模式一：用规则数量制造安全感
表现：
为了避免遗漏，把所有信息类型和异常场景全部写入 Skill。
结果：
* 模型机械枚举；
* 主目标失焦；
* 输出表面完整，实质质量下降。
修正：
只保留目标、最小方法和已经验证必要的约束。

反模式二：把 Skill 写成 Agent Runtime
表现：
* 多套状态；
* ID；
* 复杂转换；
* 结构化返回协议；
* 伪恢复机制。
修正：
语义方法留在 Skill；确定性流程交给脚本、Hook 或真实运行时。

反模式三：把 Guide 复制进 Skill
表现：
* 通用 Skill 中大量列举业务、架构、实现或测试专业内容。
修正：
Skill 说明如何使用 Guide；Guide 负责专业内容。

反模式四：父子 Skill 重复
表现：
* 父 Skill 定义完整流程；
* 子 Skill 再定义同一套流程；
* 调用后两套指令同时存在。
修正：
父 Skill 只保留调用和完成合同，把执行方法完整迁移到子 Skill。

反模式五：把文档生成理解为总结
表现：
* 文档结构完整；
* 只有高层结论；
* 关键设计细节消失；
* 后续人员仍需重新讨论如何执行。
修正：
明确 Draft 是设计固化，不是对话摘要；允许去重和重组，但不允许语义压缩。

反模式六：预先解决所有可能问题
表现：
* 没有实际失败证据，就添加大量防护规则。
修正：
只针对真实使用中观察到的错误演进 Skill。

5. 推荐的最小 Skill 结构
不是所有 Skill 都必须机械使用相同章节，但一般可以从以下最小结构开始：
---
name: <skill-name>
description: <何时使用，以及完成什么核心结果>
---

# <Skill Name>

<用一段话说明核心目标和职责边界>

## Process

1. <第一个必要动作>
2. <第二个必要动作>
3. <第三个必要动作>

## Rules

- <最关键的失败防护>
- <最关键的边界>
- <最关键的质量要求>

## Completion

<用少量条件说明什么状态下允许结束>
首版应尽量保持简短。
只有实际测试证明某个环节持续失败时，才增加相应规则或 supporting reference。

6. Skill 评审问题清单
评审一个 Skill 时，优先回答以下问题：
1. 能否用一句话说清它的核心目标？
2. 是否只承担一种主要能力？
3. 每一条规则是否直接服务于核心目标？
4. 是否存在未经实际验证的预防性设计？
5. 是否重复了 Agent 已有的通用能力？
6. 是否把专业知识错误地写进了通用 Skill？
7. 是否与父 Skill、子 Skill、Guide 或 Spec 重复？
8. 是否把可以脚本化的确定性规则留给了模型？
9. 是否引入了没有真实消费者的状态、ID 或结果协议？
10. Agent 执行时最需要记住的三件事是否足够突出？
11. 弱模型能否在当前上下文负载下持续遵循？
12. 删除一半内容后，是否仍然可以完成核心目标？
第 12 个问题尤其重要。
如果删除大量细节后核心能力仍然成立，说明原 Skill 很可能过度设计。

7. 最终原则
Skill 设计应始终遵循：
目标驱动、单一职责、最小约束、方法优先、专业外置、确定性分离、基于真实失败渐进演进。
一份好的 Skill 不追求描述所有情况，而是让 Agent 在复杂上下文中始终记住：
* 当前真正要完成什么；
* 应采用什么基本方法；
* 哪几个关键错误绝对不能发生；
* 什么状态下才算真正完成。
