# Requirement Baseline Contract

本文件定义 Requirement Baseline 的信息继承、语义表达和质量要求。它不是固定章节模板，也不限制 Requirement Baseline 只能包含本文列出的内容。

## 信息继承

Requirement Baseline 是原始需求经过验证、消歧和补充后的语义增量版本，不是原始需求摘要。

原始需求中的有效信息默认继承。只有能够明确判断属于以下情况时，才允许不保留：

- 与本次需求、需求背景及后续设计完全无关；
- 已确认是错误事实，并被正确信息替代；
- 已被用户撤回、否定或由后续结论替代；
- 与其他内容完全重复，且合并后没有语义损失。

可以重组、无损去重和澄清表达，但不得用抽象结论替代具体有效信息。删除一项信息前，检查其缺失是否会改变或迫使后续人员重新判断问题、受影响对象、现状、目标、范围、约束、验收或设计输入；会产生这些影响时必须保留。

## 最低需求语义

以下内容必须形成清楚、一致的闭环，但不是允许保留内容的上限。

### 问题与目标

- 原始问题、受影响对象及其可观察影响。
- 经过验证的需求目标，以及目标为何能够改善原始问题。
- 必要时区分期望结果与用户最初提出的候选解决手段。

### 需求边界

- 本次对哪些对象、场景、结果和既有能力变化承担责任。
- 容易被默认纳入、会造成明显范围膨胀或存在不同理解的重要排除项。
- 与目标和验收直接相关的已确认约束。

### 验收基线

- 每个核心目标对应的可观察或可判定结果。
- 足以消除多义性的参照对象、条件或业务状态。
- 核心目标和易误判边界所需的失败判定。
- 验收不得超出边界，也不得提前指定业务方案、技术实现或测试步骤。

### 用户授权后移事项

对每项后移内容表达：尚未决定的问题、可能影响的目标/边界/验收、当前建议与风险、用户已授权后移，以及第一个依赖它的设计内容冻结前这一最迟决策点。没有后移事项时直接说明没有。

## 必要上下文

保留后续设计独立理解需求所需的业务背景、领域知识和术语、已有特性、当前行为与限制、重要对象和场景、已知规则与约束，以及现状到目标状态的变化关系。

查询后已经确认、被需求分析采用，并且对理解需求、判断边界、形成验收或开展后续设计有实际价值的事实也必须保留，并附带足以定位依据的最小来源。查询过程、搜索记录、无关材料和未被采用的结果不进入 Requirement Baseline。

## 区分信息的约束力

- 用户已经确认、后续设计不得自行改变的内容，写成正式需求或约束。
- 理解需求和开展后续设计所需的背景、现状及已确认事实，作为需求上下文表达，不把它们误写为新增需求承诺。
- 原始需求中提出但尚未确认必须采用的业务流程、界面、技术、接口、数据模型或实现方向，作为未固化方案输入保留，不得删除或自动升级为需求约束。
- 仍然相关但真实性或约束力尚未确认的信息，明确其不确定身份；影响目标、范围或验收时必须解决或经用户授权后移。
- 已被修正、否定或替代的旧内容不再作为当前有效需求；具有范围约束意义的否定结论仍作为排除项或变化说明保留。
- 不得把 Agent 推断、查询未确认的信息或未授权遗漏写成确定事实。

## 表达与质量

根据需求复杂度选择清晰结构。在不损失有效信息的前提下，可以去除无价值重复、重组内容和改善表达；不追求最短篇幅，也不得把详细需求压缩为概要。

不要主动创造原始需求未提供、澄清阶段也未形成的完整 PRD、业务设计或技术设计内容。原始需求已经包含的背景、已有特性、业务规则及方案输入必须继续保留，并按其实际约束力组织。

完成标准：Requirement Draft 完整继承原始需求中的全部有效信息，加入澄清形成的新事实、解释和用户决策；问题、目标、范围和验收形成闭环；各类信息的约束力清楚；后续设计无需重新阅读原始需求或历史聊天即可理解需求并开展设计。
