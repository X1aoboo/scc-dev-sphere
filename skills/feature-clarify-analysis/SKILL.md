# Feature Clarify Analysis

分析、讨论并确认需求澄清结果。

只处理会改变需求目标、范围或验收的问题。不要创建 Task List、写文件、重写完整需求、开展业务或技术设计、执行 Review、批准或发布 Requirement Baseline。

## Process

1. **完整理解原始需求**
   完整读取原始需求及相关材料，不使用摘要、截断片段或预先提炼的结论替代源内容。
   原始需求是持续有效的基础输入。除后续已经明确修正、覆盖、否定或判定与本次需求完全无关的内容外，其余信息继续有效。

2. **形成当前整体理解**
   综合原始需求、已有材料和已经确认的信息，形成对以下内容的当前理解：
   - 原始问题及其实际影响；
   - 需求目标；
   - 范围与重要排除项；
   - 验收结果；
   - 已确认事实；
   - 可能改变需求基线的未知、矛盾或薄弱假设。
   持续检查问题、目标、范围和验收是否相互一致，不把用户提出的功能、流程或技术手段直接当作需求目标。

3. **选择最高价值问题**
   从当前未知、矛盾和薄弱假设中，选择最可能改变需求目标、范围或验收的一个问题。
   优先处理：
   - 可能导致需求目标发生变化的问题；
   - 可能造成明显范围扩大、缩小或责任变化的问题；
   - 可能改变验收结果或成功口径的问题；
   - 多个后续判断依赖其答案的问题；
   - 判断错误后返工影响较大的问题。
   不使用固定问卷，也不为了维持互动而制造问题。

4. **调查、分析并与用户确认**
   能够从现有材料或知识源查明的事实，先主动调查。需要查询时调用 `knowledge-query` Agent。
   每个高价值回合应先向用户说明：
   - 当前理解；
   - 发现的矛盾、缺口或关键假设；
   - 它对需求目标、范围或验收的影响；
   - 专业判断和建议。
   最后默认只提出一个需要用户决定或补充的问题。
   可查询事实由 Agent 负责调查，需求目标、范围承诺、成功口径、风险接受和是否后移等需求取舍由用户决定。

5. **根据回答重新校验完整需求**
   用户回答后，不只记录当前问题的答案，还要重新校验完整需求，并说明：
   - 哪些原有理解发生了变化；
   - 需求目标、范围或验收如何调整；
   - 是否影响已经确认的内容；
   - 是否产生新的关键未知或矛盾。
   随后重新选择当前最高价值问题，并继续澄清。
   用户提供模糊信息时，先给出具体理解并请求确认；只有确实存在多个实质不同的解释时，才分别说明差异。

6. **呈现并确认需求澄清结果**
   不再存在会改变需求目标、范围或验收的未决问题时，完整呈现需求澄清结果，包括：
   - 经验证的需求目标；
   - 范围与重要排除项；
   - 验收结果及必要失败判定；
   - 对原始需求的补充、修正、覆盖或否定；
   - 查询确认且对理解需求或后续设计有用的事实；
   - 已确认的需求约束；
   - 尚未固化的业务或技术方案信息；
   - 仍未确认但需要保留的信息；
   - 用户授权后移的事项、影响、风险和最迟决策点；
   - 剩余风险或薄弱假设。
   即使原始需求已经非常详细、没有发现需要继续讨论的问题，也必须呈现对目标、范围和验收的判断，并请求用户确认。
   用户提出异议或补充新信息时，恢复分析和澄清。只有用户明确确认完整需求澄清结果后，才将控制权交回 `feature-clarify`。

## Rules

- **保持原始需求完整性**：本 Skill 只形成对原始需求的补充、修正、覆盖和确认，不以摘要或重新表述替代完整原始需求。未被明确修改的原始信息继续有效。
- **保持澄清轻量**：只处理会改变需求目标、范围或验收的问题。不影响需求基线、需要通过业务或技术方案权衡回答的问题交给后续设计。
- **保留有用事实**：查询过程、搜索记录、无关结果和未采用的信息不进入需求澄清结果；查询确认且对理解需求或后续设计有用的事实必须保留。
- **保持信息身份**：原始需求中的业务或技术方案不自动升级为正式需求约束；尚未确认的信息不得写成确定事实，应保持其未固化方案、暂定理解或待确认事实的身份。
- **不得静默修改**：需要改变已经确认的需求内容时，先说明原结论、新信息、建议修改及其对目标、范围和验收的影响，再由用户确认。
- **不得静默补全或后移**：影响目标、范围或验收的未决问题必须解决，或者在说明影响和风险后，由用户明确授权后移并记录最迟决策点。
- **用户拥有需求决策权**：负责发现问题、查证事实、分析影响和提出建议，不替用户决定需求目标、范围承诺、验收口径或风险接受。

## Completion

只有同时满足以下条件，需求澄清分析才算完成：
- 原始问题与需求目标之间的关系清楚；
- 需求目标、范围和验收相互一致；
- 每个核心目标都有可观察或可判定的验收结果；
- 所有会改变需求基线的问题均已解决或获得用户授权后移；
- 对原始需求的补充、修正、覆盖和必要事实均已完整呈现；
- 未固化方案和未确认信息的身份清楚；
- 用户已经明确确认完整的需求澄清结果。
