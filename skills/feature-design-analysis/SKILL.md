# Feature Design Analysis

在 `feature-design` 当前任务“完成并确认核心设计”内执行。

只负责分析、讨论和确认当前设计。不要创建任务，不要恢复工作空间，不要写 Draft，不要执行 Lint、Review、批准或发布。

## Process

1. 基于已加载的需求、Artifact、Design Guide 和 Spec，建立当前设计理解。
2. 使用 Design Guide 的专业边界、分析透镜、必须关闭的决策、高价值矛盾和收敛标准检查当前设计。
3. 持续不断地与用户进行讨论，直到达成共识。将这一过程映射为一棵 **design tree**：每一个决策都会分支出其下的子决策。
4. 以 **轮次** 的方式处理 design tree 决策。 **frontier** 是指那些前提已经确定的每一个决策——即你**现在**可以提出的问题，而无需猜测尚未听到的答案。在一轮中提出所有**frontier** 问题：为每个问题编号，并给出你的推荐答案。然后等待用户回答，再进入下一轮。
5. 每轮用户回答都会重塑 design tree——已确定的决策会向外推进 frontier，并解除依赖这些决策的问题。重新计算 frontier，进入下一轮。如果某个问题的答案取决于本轮中仍未解决的另一个问题，则该问题属于**后续**轮次，而非本轮。
6. 查找**事实**是你的职责，而非用户的。当一个 frontier 问题需要从环境（如项目、代码、知识库等）获取事实时，**必须**创建 `knowledge-query` SubAgent 去查找——不要直接向用户询问任何你自己可以查到的信息。不要阻塞等待：正在运行的探索是一个未完成的前提条件，因此只有其下游的问题才会等待 SubAgent 返回结果——现在就处理其余的 frontier 问题。决策由用户做出——将每个问题交给他们并等待。
7. 当 frontier 为空时，结束设计讨论：访问了 design tree 中的每一分支，所有内容都已静默假设。在用户确认你已达成共识之前，请勿对此采取任何行动。
8. 按内聚主题分段呈现完整设计；每次只呈现一个 Design Section，并取得用户确认；用户确认后，将该 Section 视为已确认设计，再继续下一 Section。
9. 当用户发现遗漏、提出异议、要求修改或补充新设计点时，不得将其视为确认，先分析新输入对整体设计的影响：
    - 若只影响当前 Section，且没有引入新的未知、冲突或取舍时，修订当前 Section 并重新请求确认；
    - 若影响其他设计、引入新的不确定性或推翻既有结论时，重塑 design tree， 继续持续不断地与用户进行讨论，直到 frontier 再次为空；
    所有受到影响的已确认 Section 都必须重新确认。
10. 所有 Section 确认后，核对 Design Guide 的专业收敛标准和 Spec 核心覆盖，向用户呈现完整设计、专业覆盖结果、仍保留的假设和残余风险。
11. 只有用户明确确认当前设计已经收敛，并允许 feature-design 生成 Draft，才结束本 Skill，将控制权交还 `feature-design`。

## Rules

- 不得以“需求简单”“信息已经足够”或“后续 Review 会检查”为理由跳过分析和确认。
- 模型没有发现问题，不代表不存在问题。首次进入 Design Sections 前，至少向用户确认一次当前关键事实、假设或设计判断。
- 模板章节不是问题清单，不要机械提问。
- 每个问题必须改变或验证设计判断；不要为了增加交互而提问。
- 不得把推测、常见实践或未经核验的代码现状写成已确认事实。
- 有依据时直接挑战用户方案；不要默认接受用户提出的原因或实现方式。
- 不制造虚假替代方案；只有存在合理选择时才比较方案；已有唯一合理结论时，直接说明结论和依据。
- 新事实推翻已确认设计时，必须说明原设计、变化原因、影响范围，并重新确认受影响内容。
- 不得在本 Skill 内生成或修改正式 Draft。

## Completion

结束前必须同时满足：

- 所有适用维度已经形成明确结论；
- 不存在会实质改变设计的开放问题；
- 关键事实、假设、取舍和残余风险已经揭示；
- 完整设计已经由用户分段确认；
- 受新输入影响的 Section 已重新分析并确认；
- 用户明确确认设计已经收敛并允许进入 Draft。

不满足任一条件时，继续当前分析，不得自行宣告完成。
