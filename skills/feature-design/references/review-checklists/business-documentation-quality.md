# 业务设计文档质量评审

## 适用条件

所有 Business Design 必选。评审冻结的完整 Business Draft 是否真正讲清业务具体如何运行，使用户能够评审业务方案，使 Solution Design 和 Test Design 能在已确定的业务边界内继续工作。

## 评审规则

- 评审对象是正文中的业务功能点、现状与变化、参与者、规则、步骤、状态、异常、反馈、验收和交接，不是章节数量、篇幅、术语或图示数量。
- `blocking`：Draft 主要由目标、结论句或章节摘要组成；业务功能点缺少当前设计、本次变化或完整目标态；关键业务行为没有参与者、事实、步骤、分支和结果；用户无法评审具体业务方案；下游仍须重新补做关键业务设计；涉及人机交互却缺少用户任务、必要信息、动作、反馈或验证依据。
- `advisory`：只用于不影响独立理解和下游消费的可读性、导航、示例或低风险表达改进。
- `risk`：文档已经能够评审和消费，但用户研究、可用性证据、现状资料或运营准备仍存在已揭示的局限。
- 低影响或沿用现状可以简洁，但必须给出核验范围、事实依据、结论和无需新增业务设计的原因。
- 图、表、决策表、示例和概念原型必须承载具体关系、规则、判断或反馈；不得用数量代替设计内容。

## 检查项

- [ ] Requirement Baseline 是否拆分为可独立理解和验收的业务功能点，并与详细设计一一对应？
- [ ] 每个实质功能点是否说明当前业务设计与依据、本次新增/修改/删除，以及变化后的完整业务行为？
- [ ] 目标态是否讲清参与者基于哪些业务事实、按什么步骤和判断、面对哪些分支、得到什么业务结果？
- [ ] 规则、时间、状态、异常和验收是否与功能点形成纵向闭环，而不是散落的主题摘要？
- [ ] 存量增强是否让读者无需拼接旧文档即可理解变化后的完整业务目标态？
- [ ] Draft 是否足以让业务用户评审具体规则、责任、边界和结果，而不是只能确认一个高层方向？
- [ ] Solution Design 是否能够直接消费业务语义，Test Design 是否能够直接导出正常、异常和边界判据？
- [ ] 涉及人机交互时，是否有目标用户、关键任务、使用环境、痛点、研究或运行证据及可用性目标？
- [ ] 涉及人机交互时，是否讲清用户必须看到的信息、判断顺序、允许动作、禁止动作及正常和异常反馈？
- [ ] 空结果、部分成功、无权限、情况变化和结果尚未确认等适用状态是否不会被误解为成功或业务失败？
- [ ] 空间组织影响理解或安全操作时，是否提供可评审的低保真概念原型，并说明其确定与未确定边界？
- [ ] 图表、示例和原型是否由正文解释其关键业务含义，而非孤立展示或替代规则正文？

## Reviewer 边界

执行本 Checklist 时，对 Draft 和正式 Artifact 保持只读；findings 纳入本轮统一 Review 结果，不与用户交互，不替用户发明业务规则、用户研究结果或界面方案。评审不按最低字数、段落数、图示数或关键词出现次数判断质量，也不把未被 Requirement Baseline 承诺的额外能力当作缺陷。
