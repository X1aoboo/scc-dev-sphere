# 实现可行性评审

## 适用条件

实现设计必选。

## 评审规则

- 每个实现点建立在真实工程事实、正式契约和存在的接缝上。
- 关键行为已经设计到足以实现，不把软件结构、状态、事务或失败结果留给编码临场决定。
- 后端、前端、Worker、共享库或契约包按各自工程边界评审，不机械套用微服务检查。
- 实现细节与上游设计、机器可读契约和代码约束一致。

## 检查项

- [ ] 方案功能点、实现点、实现单元、入口和代码落点可以连续追溯。
- [ ] 受影响模块、包、文件和关键符号可定位，新增、修改、复用、废弃和删除明确。
- [ ] 软件结构、职责、依赖方向、接口、类型、输入输出和调用顺序足够明确。
- [ ] 错误、取消、超时和重试行为可实现。
- [ ] 事务、并发、顺序和幂等边界一致。
- [ ] 数据、协议、配置和部署变化具有迁移与回滚路径。
- [ ] 条件API、前端、数据、安全和运行设计仅在适用时出现，并具有足够实现信息。
- [ ] 可观测性和测试接缝能够验证返回、状态、不变量和副作用。
- [ ] 没有依赖未证实仓库能力的关键步骤。
