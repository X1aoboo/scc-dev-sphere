# 实现设计文档质量评审

## 适用条件

所有Implementation Design必选。

## 评审目标

判断Draft是否真正讲清软件如何在代码和运行环境中实现，使用户能够评审具体机制，使开发人员无需重新设计即可进入TDD。

评审对象是实现点、软件结构、代码落点、行为、类型、数据、状态、契约、失败、资源、演进和测试接缝，不是章节数量、篇幅、技术名词、表格或图示数量。

## 评审规则

- 沿每个实现点重建“上游目标—当前代码—具体变化—目标执行—最终结果”。
- 文件、类、框架和设计模式只有在说明职责、依赖与行为后才构成设计。
- 实现单元共享结构与实现点纵向行为必须描述同一目标态。
- 复杂软件关系选择合适的组件、包、类、时序、状态或运行视图；图必须由正文解释。
- API、事件、前端、数据、并发、安全、迁移和运行内容只在适用时评审，不要求空章节。
- 机器可读契约是唯一事实源，正文只解释语义与代码映射。
- 低风险变化可以简洁，但必须有核验范围、当前事实、变化、目标结果和依据。
- 不以最低字数、段落数、图示数、代码块数或关键词判断质量。

## 检查项

### 追溯与变化

- [ ] 所有Solution Design功能点是否映射到实现点、实现单元和主要入口？
- [ ] 每个实现点是否明确当前实现、本次新增/修改/复用/废弃/删除和完整目标行为？
- [ ] 代码仓、模块、文件和关键符号是否用于准确定位，而不是替代设计内容？
- [ ] 保持不变和非目标是否足以防止无关重构？

### 软件架构与结构

- [ ] 实现单元类型、构建/运行边界、组件职责和依赖方向是否明确？
- [ ] 包、组件、关键类、端口和适配器是否形成可解释的软件结构？
- [ ] 复杂结构是否有合适的图示，且图中关系与正文、代码落点一致？
- [ ] 是否明确禁止依赖、状态所有者、副作用所有者和稳定接缝？

### 实现点完整性

- [ ] 是否可以从入口开始连续说明调用、判断、分支、数据转换、状态变化、副作用和返回？
- [ ] 正常、校验失败、业务失败、技术失败、超时、取消、重复和恢复是否具有确定结果？
- [ ] 核心算法、类型、不变量和完成条件是否具体，开发人员无需临场发明？
- [ ] 设计点之间是否存在相互矛盾或隐含的第二套状态/规则？

### 数据、接口与正确性

- [ ] 数据模型、持久化、索引、唯一约束、事务和模型转换是否与行为一致？
- [ ] 错误、重试、幂等、并发、锁/版本、顺序和外部副作用是否组合成确定结果？
- [ ] 涉及跨边界契约时，机器可读定义、变更类型、兼容策略和代码映射是否完整？
- [ ] API出入参、校验、认证、租户、CSRF、幂等或版本规则是否按实际适用性定义？
- [ ] 不涉及接口或持久化时，是否没有生成虚构清单、空表或占位内容？

### 前端实现（按影响触发）

- [ ] 路由、页面、组件、Query/API Client和状态机的职责与数据流是否明确？
- [ ] 服务端状态、URL、缓存、表单、提交状态和`actionId`等客户端状态所有权是否明确？
- [ ] 加载、空、失败、无权限、冲突、未知结果和刷新后的组件行为是否确定？
- [ ] 焦点、键盘、读屏、响应式、敏感数据、遥测和构建发布是否有代码级落点？
- [ ] 是否承接已确认UCD和页面语义，而没有在实现阶段自行改写用户任务？

### 质量、运行与演进

- [ ] 性能、容量、线程、连接、队列、缓存和背压是否落到具体结构和边界？
- [ ] 日志、指标、Trace、审计、诊断和告警是否能够定位实现点和失败阶段？
- [ ] 数据、API、事件、配置和依赖的混合版本、迁移、灰度及回退是否确定？
- [ ] 安全控制是否落到输入、身份、权限、租户、数据、日志和依赖边界？

### TDD与下游消费

- [ ] 每个高风险实现点是否给出可观察行为、不变量、首个失败测试和依赖接缝？
- [ ] 测试是否证明业务结果与副作用，而不只是方法被调用？
- [ ] 单元测试不能证明的契约、集成、并发、性能和浏览器行为是否交给正确测试层？
- [ ] 开发计划是否只需拆分和排序，无需重新决定软件结构、状态、事务或失败行为？
- [ ] 文档是否能脱离聊天上下文独立阅读和评审？

## 必须阻断的表现

以下任一情况通常形成`blocking`：

- 实现单元每节只有一句结论，无法重建代码如何运行；
- 只列文件、类、方法或表名，没有职责、依赖、步骤和结果；
- 只写“使用DDD、Outbox、策略模式、状态机”等名词，没有具体机制；
- 只有横向技术主题，没有沿实现点展开当前代码、变化和目标行为的纵向实现；
- 组件图只有方框和连线，没有依赖语义、状态或正文解释；
- 关键类、状态、事务、并发或外部副作用仍需开发人员重新设计；
- 机器可读契约与正文、Controller、Client或类型映射不一致；
- 涉及前端却只有组件名称或页面截图，没有状态、数据流、失败和恢复；
- 只验证“调用发生”，不能证明返回、状态、不变量或副作用；
- 用“编码阶段决定”推迟高成本或难逆转的代码级决定。

## Finding分类

- `blocking`：关键实现机制无法连续重建，代码与契约不确定或矛盾，下游必须重新补做详细设计。
- `advisory`：设计已经可编码且闭环，但导航、图表、定位或表达仍可降低评审成本。
- `risk`：设计已经具体，但容量、外部契约、工程事实或验证环境仍有已揭示的不确定性。

## Reviewer边界

只读评审当前Draft和正式输入。不得为了通过而自行发明类、接口、状态、事务、算法或测试方案；缺口记录为finding并交回设计分析。
