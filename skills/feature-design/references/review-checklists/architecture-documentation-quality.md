# 架构文档质量评审

## 适用条件

方案设计必选。

## 评审目标

判断 Draft 是否真正讲清系统级方案具体如何实现和运行。评审对象是正文中的处理步骤、责任、契约、数据、状态、正确性、失败、质量和演进设计，不是章节数量、篇幅、专业术语或图示数量。

Draft 必须让用户能够评审具体机制，让下游在已经确定的系统边界内继续细化，而不是重新补做方案设计。

## 评审规则

- 沿需求功能点逐项重建“触发—处理—结果”的完整实现链；无法连续重建时不得通过。
- 逐项验证结论是否有具体主体、边界、步骤、数据、状态、分支和结果支撑。
- 总体方案、4+1 视图、功能点和专项章节必须描述同一目标态。
- 需求涉及用户界面时，沿用户操作重建入口、页面状态、前后端交互、失败反馈、恢复和最终可见结果；不适用时不机械生成 UI 内容。
- 图、表、Schema 和示例必须承载具体关系或规则，并由正文解释关键行为、异常和取舍。
- 同一稳定设计只在一个位置完整定义，交叉位置说明如何消费，不复制漂移。
- 低影响内容可以简洁，但必须给出核验范围、事实依据、结论和无需新增机制的原因。
- 不以最低字数、段落数、图示数或关键词出现次数判断质量。

## 检查项

### 方案全貌

- [ ] 概述是否明确目标、范围、非目标、系统定位、方案主线、主要变化和关键约束？
- [ ] 总体方案是否展开目标态系统、服务和关键组件、职责、依赖、数据所有权及核心端到端过程？
- [ ] 复杂架构关系是否有可理解的模型，且图中每个重要元素和关系都有实际语义与正文解释？

### 功能点实现

- [ ] 需求功能点清单是否覆盖正式需求，并与每个功能点详细设计双向对应？
- [ ] 每个功能点是否有具体、可验证的当前设计，而非“沿用现状”或背景概述？
- [ ] 本次变更是否定位到责任、组件、流程、接口、数据、状态、质量或运维对象？
- [ ] 是否可以仅依据目标态设计，按顺序说明从触发、判断、处理到最终结果的完整过程？
- [ ] 正常、异常、高风险、并发、重复、超时和部分失败分支是否有确定行为？
- [ ] 每个步骤是否能确定执行主体、输入、读取或写入、状态变化、输出及可观察结果？

### 架构视图

- [ ] 场景视图是否以实际场景验证端到端步骤和结果，而不是重述需求？
- [ ] 逻辑视图是否展开组件职责、依赖、逻辑数据以及行为和数据所有者？
- [ ] 进程视图是否展开运行时协作、状态、并发、超时、重试、幂等、补偿和恢复？
- [ ] 开发视图是否明确服务、代码仓或构建单元的承载关系、依赖方向和下游边界？
- [ ] 物理视图是否明确部署、实例、中间件、存储、网络、故障域、资源隔离和高可用关系？

### 接口、数据与正确性

- [ ] 每个关键跨边界交互是否明确调用方、提供方、触发、业务语义、成功、业务失败、技术失败和结果未知？
- [ ] 超时、重试、幂等、顺序、重复、乱序、兼容和恢复责任是否有唯一所有者和明确边界？
- [ ] 核心数据对象是否具有关系、所有权、写入权限、生命周期、状态转换和不变量？
- [ ] 关键步骤的数据读写、事务边界、并发竞态、唯一性和一致性机制是否具体？
- [ ] 状态图、时序图、模型或契约表是否与正文规则一致，没有引入另一套方案？

### 用户交互与前端（按影响触发）

- [ ] 是否有目标用户、关键任务、使用环境、痛点、用户研究或运行证据、待验证假设和可判定的可用性目标？
- [ ] 是否明确用户角色、任务目标、入口、导航、前置条件、退出条件和最终可见结果？
- [ ] 当前界面、具体变化和完整目标态是否都能定位到页面、交互步骤、客户端状态或前后端边界？
- [ ] 页面信息结构、区域责任、前端应用、BFF、后端服务和设计系统的责任是否清楚？
- [ ] 初始、加载、空、成功、校验失败、业务失败、技术失败、部分成功、无权限、数据过期和刷新状态是否有确定呈现与动作？
- [ ] 表单校验、错误定位、反馈时机、重复提交、并发修改、取消、离开页面和恢复行为是否明确？
- [ ] 服务端权威状态与 URL、筛选、草稿、缓存和乐观状态的所有权、生命周期及失效规则是否明确？
- [ ] 路由和操作授权、字段可见性、敏感信息、高危操作确认、审计及防滥用是否落到具体交互？
- [ ] 可访问性、响应式、国际化、兼容性、交互性能、前端监控和埋点是否有适用结论与验证方式？
- [ ] 线框图、原型或视觉稿是否有正式引用，且正文补足其无法表达的数据、权限、状态、异常和契约语义？
- [ ] 实质改变布局、信息优先级或操作方式时，是否直接展示页面地图和关键页面线框图/原型快照，而不是只用页面区域表描述？
- [ ] 是否记录目标任务 walkthrough、原型评审或用户可用性验证的参与者范围、任务、发现、设计调整和未验证假设？
- [ ] 外部设计链接是否固定版本和 Frame/页面范围，关键页面是否有随 Draft 一起冻结和评审的快照？
- [ ] 设计资产是否与 Draft、Review、人工批准和发布绑定同一版本，且正文中的相对路径可在发布与归档后继续解析？

### 可靠性、安全、质量与演进

- [ ] 每个重要故障是否说明已经成立的事实、影响、检测、隔离、恢复责任、停止条件和最终状态？
- [ ] “重试、降级、熔断、补偿、对账、告警”等机制是否明确主体、条件、边界和结果？
- [ ] 资产、信任边界、身份、租户、权限、敏感数据、威胁路径和控制是否落到实际架构位置？
- [ ] 每项重要质量属性是否具有负载与环境、可判定目标、架构措施、容量依据和验证方式？
- [ ] 部署、混合版本、发布顺序、迁移、灰度、回退和已有数据或事件的处置是否具体？
- [ ] 关键决策是否包含评价标准、候选方案、依据、代价、限制和风险，而不只给出技术名称？

### 评审与下游消费

- [ ] 用户是否有足够具体的方案、边界、异常和取舍可以评审，而不是只能确认概括性结论？
- [ ] Implementation Design 是否只需细化模块、类、物理模型和代码，而无需重新决定系统级流程、接口、状态、事务或失败语义？
- [ ] Test Design 和运维是否能直接提取必须验证的场景、质量目标、告警、恢复和上线约束？
- [ ] 文档是否能脱离聊天上下文独立阅读，没有遗漏、过度概括、语义变化或擅自新增设计？

## 必须阻断的表现

以下任一情况通常形成 `blocking`：

- 只写采用某项技术或增加某个组件，没有说明具体如何工作；
- 架构图只有方框和连线，没有职责、交互、数据或失败语义；
- 功能点只有目标、变化和一句目标态结论，没有完整处理步骤；
- 只有 Happy Path，没有异常、并发、重复和恢复；
- 只列接口名、字段名或事件名，没有业务结果和可靠交互契约；
- 只列数据实体，没有关系、状态、不变量和一致性边界；
- 需求改变用户界面，但只有页面名称、静态截图或 Happy Path，没有页面状态、前后端责任、失败反馈和恢复行为；
- 把用户可见行为、客户端与服务端状态边界、操作权限或并发提交语义全部推给前端实现阶段；
- 实质改变界面但没有 UCD 依据、关键页面线框图/原型快照或任何面向目标任务的验证；
- 关键界面只存在于可变外部链接，未随 Draft 版本化并纳入 Review 和人工批准；
- 只写“幂等、重试、降级、告警”，没有主体、条件、边界和最终状态；
- 只有性能或可用性形容词、孤立数值，没有环境、机制和验证；
- 用“实现阶段细化”推迟本应由方案设计确定的系统级问题；
- 下游必须重新发明跨服务流程、事务、数据状态或失败恢复。

## Finding 分类

- `blocking`：重要方案无法按步骤重建；具体机制、稳定契约、正确性或失败闭环缺失；章节间相互矛盾；下游必须重新补做系统级方案。
- `advisory`：方案已经具体、闭环且可消费，但组织、定位或表达方式仍可明显降低阅读和评审成本。
- `risk`：方案已经具体表达，但受外部证据、待验证容量、模型精度或环境条件限制，仍有已揭示的不确定性。

## Reviewer 边界

只读评审当前 Draft 和相关正式输入。不得为了让文档通过而自行新增架构选择、处理步骤、契约、状态、质量目标或实现机制；发现缺口时记录 finding 并交回设计分析。
