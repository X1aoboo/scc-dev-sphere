# 方案设计指南

## 专业边界

以特性整体为主语，设计特性在系统、服务和服务级关键组件层面**具体如何实现和运行**。方案设计必须确定端到端流程、责任、交互契约、逻辑数据与状态、事务与一致性、并发与失败行为、质量措施、部署和演进边界。

下游 Implementation Design 继续细化服务内部模块、类、方法、物理表与索引、代码组织和逐文件步骤。下游可以选择局部实现手段，但不得重新决定系统责任、跨服务流程、稳定接口、数据所有权、状态不变量、事务边界、失败语义或质量目标。仍需下游自行决定这些问题时，Solution Design 尚未完成。

按当前目标采用相关 Requirement、Business Design、既有设计、代码和运行事实。任何特定 Design Type 的 Baseline 都不是固定前置条件；缺少会改变方案判断的事实时，先调查或揭示阻断缺口，不得用假设性实现掩盖。

## 设计场景

### 新建特性

从目标、场景、系统环境和既有工程约束建立完整目标态。说明新责任如何进入现有系统，如何调用、读写、部署、失败和恢复，以及相邻能力为什么无需改变。

### 存量特性增强

先从正式设计、代码、接口规范和运行事实建立与本次功能点直接相关的可信现状，再区分：

- **新增**：本次引入的场景、责任、组件、契约、数据、状态、质量机制和运维能力；
- **修改**：行为、边界、状态、接口、数据、部署或质量语义的具体变化；
- **删除**：被移除的路径、责任、契约、数据和兼容处理；
- **保持不变**：受影响范围内继续有效且必须保护的既有行为和稳定边界；
- **非目标**：当前方案明确不承担的能力与演进范围。

最终方案描述变化后的完整目标态，不能只提供改动清单。

## 专业原则

- 方案的核心是“具体怎么做”，不是技术名词、架构结论或组件清单。
- 先形成端到端实现链，再从 4+1 和专项设计验证同一方案。
- 以需求功能点形成纵向主线；每个功能点都能从触发连续走到结果。
- 每项复杂度都服务于明确需求、约束、质量属性或风险。
- 系统边界、服务职责、依赖方向、数据所有权和写入权限相互闭合。
- 正常、异常、并发、重复、超时、部分失败、恢复和版本混用都有确定行为。
- 稳定接口说明业务语义和失败语义，不只列路径、字段名或消息名。
- 逻辑数据设计说明关系、状态、不变量、读写和一致性，不只列实体名称。
- 质量属性使用刺激、环境、可判定目标、架构措施和验证方式表达。
- 同一设计只在一个位置完整定义，其他位置说明作用并引用。
- 图、表、Schema 和示例承载设计关系，正文解释规则、边界、异常和取舍。

## 功能点分析透镜

从需求、场景和业务结果识别能够独立说明系统级实现结果的功能点。功能点不是原始需求、User Story、代码模块或实施任务的机械映射：一个功能点可以覆盖多个细粒度需求，一个复杂需求也可以拆成多个功能点。

每个功能点先建立：

- 关联需求、预期结果、主要场景、范围和非目标；
- 与本次变化直接相关的当前行为、参与者、接口、数据、状态和质量表现；
- 新增、修改、删除、保持不变的具体对象；
- 与其他功能点的前置、调用、数据、状态或结果依赖。

然后形成完整的**实现链**：

1. 触发与前置条件；
2. 参与系统、服务和关键组件及其责任；
3. 按顺序执行的处理步骤、判断和分支；
4. 每一步读取、创建、修改的数据和状态；
5. 跨边界接口、事件及成功与失败结果；
6. 事务、并发、幂等和一致性保障；
7. 异常、超时、重复、部分失败与恢复；
8. 最终业务结果、审计和可观察信号；
9. 部署、兼容、迁移、回退及下游约束。

只写“采用 Outbox”“增加重试”“通过缓存优化”“引入状态机”不是实现链。必须继续确定这些机制由谁执行、在哪个边界生效、处理什么状态、如何应对失败，以及如何证明结果正确。

并非每个功能点都需要机械覆盖全部维度；不适用维度要有可核验依据。适用维度缺少具体机制时不得收敛。

## 4+1 分析透镜

4+1 用于解释和交叉验证已经形成的目标态，而不是用五段概述代替方案：

- **场景视图**：以代表性正常、异常和高风险场景验证端到端实现链，呈现触发者、步骤、分支和可观察结果。
- **逻辑视图**：展开系统、服务和关键组件、职责、依赖、逻辑数据、行为所有者和数据所有者。
- **进程视图**：展开运行时调用、异步协作、状态变化、并发、超时、重试、幂等、补偿、降级和部分失败。
- **开发视图**：说明能力落在哪些服务、代码仓、构建单元和公共能力中，以及依赖方向和内部设计边界。
- **物理视图**：说明部署单元、实例关系、中间件、存储、网络与信任边界、故障域、资源隔离、扩缩容、高可用和运维关系。

C4、组件图、时序图、状态图、活动图、数据流图和部署图是表达工具。当语义图能明显降低理解成本时，使用合适的 Mermaid 语义图并由正文解释关键规则。不要求每份设计必须包含图示，也不规定图示数量；界面设计、视觉设计等不适合 Mermaid 的内容不强制绘图，禁止用 ASCII 字符模拟语义图。

## 用户交互与前端设计透镜

当需求新增或改变用户可见界面、交互流程或客户端行为时，以用户为中心的设计（UCD）和前端方案都是目标态的一部分，不得只写“新增页面”“调用接口”或把全部内容推给 Implementation Design。UCD 不是为既定技术方案补一张效果图；先使用正式用户研究、现状观察、支持工单、可用性数据或明确待验证假设理解用户、任务和使用环境，再形成并验证设计。

按实际影响确定：

- 目标用户、关键任务、使用环境、痛点、研究证据、待验证假设和可判定的可用性目标；
- 用户角色、任务目标、入口、导航、前置条件、退出条件和最终可见结果；
- 与本次变化相关的当前页面、交互步骤、客户端状态和问题位置；
- 页面信息结构、区域责任、前端应用、BFF、后端服务及设计系统之间的边界；
- 初始、加载、空、成功、校验失败、业务失败、技术失败、部分成功、无权限、数据过期和刷新后的界面状态；
- 表单规则、校验位置、错误定位、反馈时机、重复提交、并发修改、离开页面和恢复行为；
- 服务端权威状态与 URL、筛选条件、草稿、缓存、乐观状态等客户端状态的所有权、生命周期和失效规则；
- 身份、路由和操作授权、字段可见性、敏感信息、高危操作确认、审计和防滥用；
- 可访问性、响应式、国际化、浏览器或终端兼容、交互性能、埋点和用户侧诊断。

用户旅程、导航和状态转换适合使用流程图或状态图；页面布局、信息优先级和视觉层级使用线框图、原型、截图或标注图，并在 Draft 中直接展示关键页面。页面区域表可以补充责任和数据来源，但不能在布局会影响理解或操作时替代线框图。Mermaid 不用于替代线框图或视觉稿。

关键设计至少经过一次面向目标任务的 walkthrough、原型评审或用户可用性验证，并记录参与者范围、任务、发现、设计调整和仍未验证的假设。外部原型或视觉稿必须固定版本、Frame/页面范围和访问位置；关键页面同时保留评审快照，不能依赖一个可被静默覆盖的链接。

Solution Design 固定用户可见行为、信息结构、关键页面布局、页面状态、前后端责任和稳定交互契约；像素、样式 Token 和组件内部代码可以由产品/视觉设计或下游实现继续细化。

不涉及用户界面时，只需给出核验范围和不适用依据，不生成空页面清单。

## 必须关闭的系统级设计

1. **责任与流程**：谁触发、谁编排、谁决定结果、谁拥有副作用，完整步骤和分支是什么。
2. **接口与集成**：调用方、提供方、字段业务语义、成功、业务失败、技术失败、权限、超时、重试、幂等、兼容和恢复责任。
3. **数据与状态**：逻辑对象、关系、权威来源、写入权限、生命周期、状态转换、不变量、读写路径和保留规则。
4. **正确性机制**：事务边界、并发竞态、唯一性、一致性、重复、乱序、补偿和对账如何处理。
5. **可靠性与运维**：故障模式、影响、检测、隔离、降级、自动恢复、人工出口、可观测信号和运行责任。
6. **安全与隐私**：资产、信任边界、身份权限、输入、敏感数据、威胁路径、控制、审计和攻击后的恢复。
7. **质量属性**：负载与环境假设、可判定目标、架构措施、容量依据、验证方式和代价。
8. **部署与演进**：部署关系、故障域、版本兼容、发布顺序、灰度、迁移、回退和混合版本行为。

方案设计必须关闭这些系统级语义；类、方法、DDL 和逐文件实现仍留给下游。

## 高价值矛盾

- 文档声明采用某项技术，却没有说明具体如何使用以及如何保证正确。
- 架构图只有方框和连线，没有职责、关系语义、数据或失败行为。
- 功能点只有目标和改动，没有可按步骤重建的目标态实现链。
- 当前设计没有事实依据，目标态因而无法说明具体改在哪里。
- 正常路径成立，但重复、并发、乱序、超时、部分失败或版本混用时没有确定结果。
- 服务承担责任却不拥有所需行为、数据或写入权限。
- 接口只有字段或调用名称，没有业务结果、失败和恢复责任。
- 数据只有实体清单，没有关系、状态、不变量、事务和一致性边界。
- “幂等、重试、降级、告警”只有名词，没有主体、条件、边界和最终状态。
- 需求改变用户界面，但文档只有页面名称或正常操作，没有页面状态、前后端责任、失败反馈和恢复行为。
- 线框图或视觉稿只展示静态布局，却没有说明权限、数据来源、交互规则和异常状态。
- 需求实质改变界面，却没有用户研究或假设依据、关键页面线框图以及任何 walkthrough、原型或可用性验证。
- 关键界面只引用可变外部链接，没有版本、范围和随 Draft 冻结的评审快照。
- 质量目标只有形容词或数值，没有负载环境、架构措施和验证。
- 把本应由 Solution Design 确定的系统级问题推给“实现阶段细化”。
- 五个视图、功能点和专项章节描述的不是同一套方案。
- 不可逆成本和残余风险没有进入用户决策。

## 风险缩放

设计深度取决于架构影响，不取决于需求标题、文档篇幅或新建/增强标签。跨系统协作、数据所有权变化、状态复杂度、信任边界、容量与可用性目标、外部依赖、多版本并存、不可逆选择和广泛存量影响越多，实现链、契约、失败和演进设计越需要完整展开。

局部低风险方案仍检查全部固定维度；没有实质影响时，以核验范围、结论、依据和无需新增机制的原因简洁表达。

- 始终执行：[architecture-consistency](../review-checklists/architecture-consistency.md)、[architecture-documentation-quality](../review-checklists/architecture-documentation-quality.md)、[design-traceability](../review-checklists/design-traceability.md)。

- 跨进程、网络、队列、存储或可用性边界影响正确性时执行：[reliability-review](../review-checklists/reliability-review.md)。
- 存在信任边界、身份、权限、秘密、外部输入、敏感数据或滥用路径时执行：[security-review](../review-checklists/security-review.md)。
- 生产运行、诊断、发布、回滚、容量或值守责任受到影响时执行：[operability-review](../review-checklists/operability-review.md)。

固定章节不自动触发条件 Checklist；按实际设计影响判断适用性。

## 专业收敛标准

- 需求已经拆成边界清楚的功能点，清单和详细设计双向覆盖。
- 每个适用功能点都有完整实现链，读者可以从触发按步骤走到最终结果。
- 存量功能点的当前设计、具体变化和完整目标态均有事实支撑。
- 总体架构、五个 4+1 视图、功能点和专项设计描述同一目标态。
- 责任、接口、数据、状态、事务、并发、失败、质量和演进无需下游重新猜测。
- 涉及用户界面时，用户旅程、信息结构、页面状态、前后端边界和交互失败语义已经闭合。
- 涉及实质界面变化时，关键页面可直接看见，UCD 依据、设计理由、验证结果和未验证假设均可评审。
- 所有适用系统级设计已形成具体机制、边界、结果和验证方式。
- 图表与正文共同承载方案，没有用辅助表达或专业术语代替设计。
- Implementation Design 只需在已确定边界内细化服务内部实现。
- 关键取舍、不可逆代价、假设和残余风险已经确认。
- 方案能够脱离聊天上下文，由用户评审并由下游直接消费。
