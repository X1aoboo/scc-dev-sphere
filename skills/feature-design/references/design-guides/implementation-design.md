# 实现设计指南

## 专业边界与定位

实现设计是代码级 Detailed Design。它以已批准的 Solution Design、真实代码与工程事实为输入，把系统责任细化为开发人员无需重新设计即可进入 TDD 的目标实现。

实现设计不等于微服务设计。实现单元是具有明确构建、所有权或运行边界的工程对象，可以是：

- 后端服务、单体模块、Worker、批处理或 CLI；
- 前端应用、页面 Feature 或独立构建单元；
- 共享库、SDK、契约包或迁移工具；
- Solution Design 明确需要独立实现和验证的其他单元。

Solution Design 决定系统责任、跨单元流程、数据所有权、外部契约和系统级正确性；实现设计决定包、组件、类、函数、物理模型、代码级控制流、资源和测试接缝。真实工程事实要求改变上游结论时，明确记录依据并升级，不能在代码设计中静默改写。

实现设计产出完整目标态及必要变化，不是文件清单、代码 Diff 或开发任务列表。私有方法和不影响协作、正确性、迁移或测试的局部选择留给编码。

## 设计场景

### 存量实现单元

建立连续映射：

```plantuml
@startuml
left to right direction
rectangle "当前代码与运行事实" as Current
rectangle "受影响实现点" as Impact
rectangle "完整目标实现" as Target
rectangle "新增、修改、复用、废弃、删除" as Change
Current --> Impact
Impact --> Target
Target --> Change
@enduml
```

调查实际入口、调用链、数据、状态、依赖、测试、构建和运行能力。正文必须让读者看清现状、变化及变化后的完整行为；文件和符号用于定位，不能替代设计。

### 新增实现单元

以已确认的技术栈、脚手架、共享能力、参考实现和部署基线建立目标结构。只引入当前责任需要的模块、抽象和模式，并明确首个可验证行为、外部接缝、数据状态、错误资源边界和运行能力。

### 不同实现单元类型

- 后端重点关闭应用入口、领域行为、持久化、事务、并发、外部副作用和运行资源。
- 前端重点关闭路由、组件职责、客户端状态、数据流、API Client、界面状态、可访问性、安全、构建和遥测。
- 契约或共享库重点关闭兼容边界、生成物、消费者、版本策略和禁止依赖。
- 不适用的类型专属内容不生成空章节。

## 专业原则

### 纵向可编码

每个实质变化沿一个实现点讲清：上游目标、当前实现、本次变化、代码落点、目标执行、数据状态、契约、失败分支和可观察结果。横切章节补充共享约束，不能代替纵向实现。

### 软件结构先于文件清单

先确定组件、包、关键类、职责和依赖方向，再定位文件。类名、模式名和技术名词只有在说明具体协作机制后才构成设计。

### 正确性与显式契约

使用接口、类型、不变量、状态转换、约束和错误模型表达关键行为。相同输入与状态产生确定结果；时间、随机、并发和外部依赖具有明确边界。

### 简单、正交和稳定依赖

选择满足当前需求与已确认演进约束的最简单结构。共同维护同一不变量的行为保持内聚，独立变化的职责保持分离；稳定核心不依赖框架、数据库或外部服务细节。

### 模式按需使用

采用设计模式时说明真实矛盾、直接实现的不足、模式带来的结构收益和复杂度成本。直接实现足够时，“不采用模式”是有效结论。

### TDD作为设计反馈

设计定义可观察行为、不变量和依赖接缝，使开发可以从失败测试开始。测试不应依赖私有方法、脆弱调用顺序或为了 Mock 而泄漏的内部结构。

## 实现单元与实现点主线

### 实现单元

实现单元用于表达工程边界和共享结构。每个上游分配的责任都必须映射到一个实现单元、代码仓/工程、构建产物和正文位置。

同一单元内只定义一次共享的：

- 软件结构、包边界和依赖规则；
- 数据库、线程池、连接池、配置和运行约束；
- 通用错误、观测、兼容和发布机制；
- 测试基础和禁止依赖。

### 实现点

实现点是可独立评审的行为或变化切片，通常对应一个或多个 Solution Design 功能点。每个实质实现点必须能够回答：

1. 承接什么需求、方案功能点和不变量；
2. 当前代码在哪里、如何运行、存在什么差距；
3. 新增、修改、复用、废弃或删除哪些工程对象；
4. 目标组件、关键类型和依赖如何协作；
5. 从入口到结果的控制流、数据流和状态变化；
6. 接口、持久化、副作用、事务和并发如何处理；
7. 正常、异常、重复、超时、取消和恢复结果是什么；
8. 首个失败测试、可观察结果和完成标准是什么。

实现点不要求机械采用同一小节标题，但上述内容必须能从正文连续重建。

## 分析透镜

- **工程追溯**：Solution 功能点 → 实现点 → 实现单元 → 代码仓/工程 → 包、文件和符号。
- **软件结构视图**：组件、包、关键类、接口、依赖方向和禁止依赖。
- **运行时交互**：入口、调用顺序、同步/异步边界、线程、事务和外部副作用。
- **数据与状态**：模型转换、所有权、状态机、表、索引、唯一约束和生命周期。
- **故障与竞争**：错误、超时、重试、重复、乱序、并发、部分成功和恢复。
- **资源与算法**：复杂度、规模、批量、内存、I/O、连接、队列、背压和过载。
- **契约与演进**：API、事件、配置、依赖、Schema、混合版本、迁移和回退。
- **前端实现**：路由、组件、状态所有权、数据获取、焦点、可访问性、安全和构建。
- **TDD行为切片**：可观察行为、不变量、依赖隔离和跨测试层边界。

图示用于降低理解成本时采用 PlantUML。复杂组件/包关系、关键类协作、跨边界时序、状态机和运行资源拓扑通常适合绘图；不要求每份设计都包含图示，也不规定图示数量。图必须由正文解释其责任、交互和约束。禁止使用 ASCII 字符模拟语义图；界面设计、线框图或视觉稿等不适合 PlantUML 的内容不强制使用 PlantUML。

## 必须关闭的代码级决策

### 1. 工程事实与变化边界

定位当前工程、模块、入口、调用链、关键符号、数据和测试。区分新增、修改、复用、废弃、删除、保持不变和非目标。

### 2. 目标软件结构

定义组件、包、关键类、职责、公开边界、依赖方向、适配器、状态和副作用归属。复杂关系应选择组件图、包图、类图或运行拓扑表达，不以目录树代替架构。

### 3. 实现点行为

逐项给出当前实现、具体变化、目标执行步骤、分支、输入输出、数据状态、副作用和最终结果。开发者不得还需自行发明核心算法、状态转换或调用顺序。

### 4. 接口、类型与契约

定义关键内部接口、类型、空值、错误、不变量和模型转换。

只有涉及跨边界 API、事件或其他集成契约时才展开契约设计：

- 方案阶段已确认的机器可读契约是唯一事实源；
- 实现设计映射到 Controller、Client、DTO、Mapper、校验和测试；
- 新增、修改、复用、废弃和删除具有兼容与迁移结论；
- 不涉及接口时不生成空 API 清单。

### 5. 数据、状态与持久化

定义数据结构、状态转换、表、字段、索引、唯一约束、Repository/DAO、事务写入和数据生命周期。没有持久化影响时记录核验结论，不生成虚构模型。

### 6. 错误、并发、事务与一致性

定义异常转换、超时、取消、重试责任、幂等键、竞争对象、锁/版本、事务范围、外部副作用、顺序、部分成功、补偿和人工恢复。

### 7. 技术质量、运行与演进

把安全、性能、容量、可观测性、资源隔离、配置、部署、兼容、迁移、灰度和回退落实到具体代码及运行机制。

### 8. 前端实现（按影响触发）

涉及界面时，承接已确认的UCD和方案页面结构，定义路由、组件、客户端状态、API数据流、加载/空/失败/冲突/未知结果、焦点与读屏、敏感数据、遥测和构建发布。实现设计不重新进行用户研究或改写页面业务语义。

### 9. TDD与下游交接

为每个高风险实现点定义关键行为、不变量、首个失败测试、依赖接缝和完成标准。Development Implementation Plan只需拆分、排序和执行，不得重新决定关键设计。

## 高价值矛盾

- 上游责任与真实代码边界不一致；
- 实现点无法从当前代码连续推导到目标行为；
- 目录或类清单没有形成可解释的软件结构；
- 组件职责、依赖方向、状态所有权和事务边界冲突；
- 接口契约与实现类型、校验或错误模型不一致；
- 并发、幂等、重试和外部副作用组合后没有确定结果；
- 前端根据日志或客户端状态重新推导服务端业务事实；
- 模式或抽象没有真实变化点，只增加间接层；
- 兼容、迁移、混合版本和回退互相矛盾；
- 单元测试只能验证调用发生，不能证明行为与不变量；
- 内容退化为摘要、文件清单、技术名词或任务计划。

架构级矛盾升级回 Solution Design；实现单元内部矛盾在本设计中关闭。

## 风险缩放

深度由正确性、并发、数据、外部副作用、迁移、资源、前端交互和运行风险决定，不由文件数、篇幅、实现单元类型或图示数量决定。

局部低风险变化可以简洁，但必须保留核验范围、当前事实、变化、目标结果和无需新增机制的理由。条件内容只在适用时出现，不生成空章节。

## 专业收敛标准

- 所有上游责任都映射到实现单元和实现点；
- 每个实质实现点都能从当前代码连续重建到目标行为和结果；
- 软件结构、关键类、依赖方向、控制流、数据、状态和持久化一致；
- 条件 API、前端、迁移、安全和运行内容按实际影响完整展开；
- 错误、超时、重试、幂等、并发、事务、顺序和恢复行为确定；
- 机器可读契约与代码映射一致，没有两份事实源；
- 关键行为能够由TDD切片和后续测试直接验证；
- 用户可以评审具体实现机制，开发计划无需重新设计；
- 文档脱离聊天上下文仍能独立理解。
